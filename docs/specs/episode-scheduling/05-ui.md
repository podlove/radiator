# 05 – User Interface

Admin area, Phoenix LiveView + DaisyUI/Tailwind in legacy. All UI strings via `gettext`.

Routes:

- `/admin/podcasts/:podcast_id/episodes` — episode list
- `/admin/podcasts/:podcast_id/episodes/new` — episode form (create)
- `/admin/podcasts/:podcast_id/episodes/:id/edit` — episode form (edit)
- `/admin/podcasts/:podcast_id/episodes/:id` — episode show page with availability matrix

## 1. Episode form (new / edit)

Fields: title, subtitle, summary, number, iTunes type, duration — plus two fieldsets.

### 1.1 Proposals fieldset

- Shown while the episode is in state `:scheduling` (new episodes default to it).
- Edit form loads existing proposals as rows.
- **"Add Proposal"** button:
  - requires the current user to have a persona; otherwise flash error
    *"You need a persona before you can propose dates."* and nothing is added
  - if the episode has no scheduling form yet, one is created on the fly with
    `owner_persona_id = current persona`
  - appends a row with a date/time input and hidden `created_by_persona_id = current persona`
- Each row has a remove (✕) button that removes only that row.
- Rows are read-only (or hidden) when the scheduling is `:closed`.
- The date/time input is local time of the user (intended: browser/user time zone, converted to UTC
  on save; see [07](./07-known-gaps-and-decisions.md) #4). A date picker (e.g. DaisyUI + Cally) is
  desirable.
- Saving:
  - with ≥1 proposal row → episode + scheduling (status `:open`) + proposals are created/updated
  - with no proposal row → episode is saved without scheduling
  - success → flash *"Episode saved"* and navigate to the episode show page
  - failure → flash *"Could not save episode"*, form keeps the input and shows errors

### 1.2 Participants fieldset

- Candidate chips: personas that participated in other episodes of the same podcast, excluding
  those already in the form. Clicking a chip adds that persona as a participant row.
- "Add Participant" adds an empty row (name + handle) → new persona is created on save, or an
  existing one is related when the handle matches (handle is unique).
- Each row has a remove button; removing un-relates the persona from the episode.
- Intended: on save, the scheduling's `participant_persona_ids` is synchronized with the episode
  participants.

## 2. Episode show page

Header (number, title, subtitle, Edit / Delete buttons), summary, detail list, then the
**Availability** section (only when the episode has a scheduling), then the **Participants** list
(*"No participants yet"* when empty).

### 2.1 Availability matrix

```
                     ┌──────────────┬──────────────┬──────────────┐
                     │  🏆          │              │              │
                     │  Fri         │  Sat *       │  Sun *       │   * weekend column (bg-base-200)
                     │  17.04.2026  │  18.04.2026  │  19.04.2026  │   🏆 winner (border-2 border-primary)
                     │  19:00       │  10:00       │  19:00       │
─────────────────────┼──────────────┼──────────────┼──────────────┤
Alice                │      ✓       │      ✓       │      ✗       │
Bob (you)            │  [✓][?][✗]   │  [✓][?][✗]   │  [✓][?][✗]   │
Carol                │      ?       │      –       │      ✓       │
─────────────────────┼──────────────┼──────────────┼──────────────┤
SCORE                │     +2       │     +1       │      0       │
```

**Columns** = proposals sorted by `datetime` ascending (chronological — *not* by rank). Header shows:

- trophy icon if the proposal is the winner (see [03 §5](./03-ranking-and-stats.md#5-winner-ui-highlight)), with accessible label *"Top proposal"*
- weekday short label (localized; legacy hard-codes German `Mo Di Mi Do Fr Sa So`)
- date `dd.mm.yyyy`, time `HH:MM` (intended: in the viewer's time zone)
- badge *"Chosen"* when the scheduling is closed and this is the chosen proposal
- weekend (Sat/Sun) columns get a background highlight in header, cells and footer

**Rows** = scheduling participants, sorted by `public_name`. The current user's row is marked
*"(you)"*. Empty state: one row *"No participants yet"* spanning all columns.

**Cells**

- Own row: three buttons yes (✓) / maybe (?) / no (✗). The button matching the current vote is
  highlighted (`btn-success` / `btn-warning` / `btn-error`), the others are neutral (`btn-ghost`).
  All three are `disabled` unless `can_vote?` ([04 §3](./04-authorization.md#3-ui-gating-can_vote)).
- Other rows: icon ✓ (success color), ? (warning color), ✗ (error color), or a faint "–" when pending.

**Footer** = *"Score"* row with each proposal's `total_score`, sign-prefixed (`+2`, `0`, `-1`),
monospace; the winner's cell is bold and bordered.

**Layout**: table wrapped in a horizontally scrollable container; the name column is sticky
(`sticky left-0`) so it stays visible on mobile.

### 2.2 Voting interaction

- Clicking a button sends `vote` with `proposal-id` and `score` (`"1"`, `"0"`, `"-1"`).
- The server parses the score and whitelists `-1/0/1`; then calls the `vote` action with the
  current persona and the current user as actor.
- Success → matrix re-renders with the new state and updated footer/winner.
- Any failure (invalid score, closed scheduling, not a participant, no persona) → flash
  *"Could not record your vote."*; nothing is written.
- Clicking the active button again is allowed (no-op). v1 has no explicit "unvote" button in the UI
  (the `remove_vote` action exists; optional: clicking the active button removes the vote).

### 2.3 Owner controls (intended, not present in the legacy UI)

Visible only to the owner:

- **Ranking panel** (open scheduling): proposals in ranking order ([03 §3](./03-ranking-and-stats.md#3-ranking-order))
  with total score and yes/maybe/no/pending counts; top proposal marked; hint when tied;
  hint when not everybody has voted (`all_voted? == false`).
- **"Choose this date"** per proposal (open) → `finalize`, with confirmation dialog.
- **"Reopen scheduling"** (closed) → `reopen`, with confirmation dialog.

Optional for participants (open): an "Add date" input calling `add_proposal`, and a remove button
on proposals they created (owner: on all proposals).

## 3. Freshness

After a vote the acting user's view is refreshed. Other viewers see changes on reload (v1).
Realtime broadcast via PubSub is out of scope but the matrix should be built so it can be
re-rendered from a pushed scheduling.
